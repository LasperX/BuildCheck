## บทที่ 3 การวิเคราะห์และออกแบบระบบ

### 3.1 ภาพรวมและสถาปัตยกรรมของระบบ

BuildCheck เป็นเว็บแอปพลิเคชันจัดสเปกคอมพิวเตอร์ภาษาไทย ผู้ใช้เลือกอะไหล่ทีละหมวด 8 หมวด (CPU, เมนบอร์ด, แรม, การ์ดจอ, อุปกรณ์เก็บข้อมูล, PSU, เคส, ชุดระบายความร้อน) แล้วระบบตรวจทันทีว่าอะไหล่ใส่ด้วยกันได้หรือไม่ กำลังไฟพอหรือไม่ และราคารวมเท่าไหร่ ทั้งแบบมือหนึ่งและมือสอง

**รูปที่ 3.1 สถาปัตยกรรมระบบ** → `docs/diagrams/img/architecture.png`

ระบบแบ่งเป็น 3 ส่วน

| ส่วน | เทคโนโลยี | หน้าที่ |
|---|---|---|
| ส่วนแสดงผล (Frontend) | Next.js 16 (App Router) + React 19 + Tailwind CSS 4 | หน้าเว็บทั้งหมด จัดสเปกในเบราว์เซอร์ได้ทันทีโดยไม่ต้องล็อกอิน |
| ส่วนประมวลผล (Backend) | Next.js Server Actions และ Route Handlers บน Vercel (เซิร์ฟเวอร์สิงคโปร์ `sin1`) | ตรวจสิทธิ์ ตรวจค่าที่รับเข้ามา อ่านและเขียนฐานข้อมูล |
| ฐานข้อมูล | PostgreSQL 18 บน Neon (สิงคโปร์) ผ่าน Drizzle ORM | เก็บอะไหล่ สเปกของสมาชิก ชุมชน ราคามือสอง และบันทึกการทำงาน |

**จุดเด่นของการออกแบบ:** ระบบตรวจความเข้ากันได้ (Compatibility Engine) เขียนเป็นฟังก์ชันล้วนที่ไม่อ่านฐานข้อมูลเอง จึงรันได้ทั้งในเบราว์เซอร์ (ผลขึ้นทันทีที่เลือกอะไหล่) และบนเซิร์ฟเวอร์ (ตรวจซ้ำตอนบันทึก ไม่เชื่อผลจากหน้าเว็บ) โดยใช้กฎชุดเดียวกัน

### 3.5 การออกแบบระบบตรวจความเข้ากันได้

**รูปที่ 3.10 Flowchart การตรวจความเข้ากันได้** → `docs/diagrams/img/flow-check.png`

กฎตรวจมี 3 ระดับ: **ผิดพลาด** (ใส่ด้วยกันไม่ได้) · **เตือน** (ใส่ได้แต่มีความเสี่ยง) · **ข้อมูล** (ข้อควรรู้)

**กฎหลัก 18 ข้อ (R01–R18)**

| รหัส | ตรวจอะไร |
|---|---|
| R01–R03 | Socket ของ CPU กับเมนบอร์ด และรุ่น CPU ที่บอร์ดรองรับ (รวมกรณีต้องอัปเดต BIOS) |
| R04–R07 | ชนิดแรม จำนวนแถว ความจุรวม และความเร็วแรมเทียบกับเมนบอร์ด |
| R08–R11 | ขนาดเมนบอร์ด ความยาวการ์ดจอ ความสูงซิงก์ลม และขนาดหม้อน้ำเทียบกับเคส |
| R12–R13 | ชุดระบายความร้อนรองรับ Socket และ TDP ของ CPU |
| R14–R16 | กำลังไฟรวมเทียบ PSU (ผิดพลาดเมื่อเกิน เตือนเมื่อเผื่อไม่ถึง 30%) ขนาด PSU กับเคส และหัวต่อไฟการ์ดจอ |
| R17 | จำนวนช่อง M.2 และพอร์ต SATA |
| R18 | CPU ไม่มีกราฟิกในตัว แต่ไม่ได้เลือกการ์ดจอ |

**กฎมือสอง 6 ข้อ (U01–U06)** ตรวจเฉพาะชิ้นที่เป็นมือสอง เช่น PSU มือสองอายุมาก แพลตฟอร์มที่ Socket เลิกผลิต และราคาที่ผู้ขายเสนอถูกผิดปกติ (ไม่มีข้อไหนเป็นระดับผิดพลาด เพราะของมือสองยังใช้งานได้ ระบบแค่เตือนให้ตรวจก่อนซื้อ)

**สูตรคำนวณกำลังไฟ**

> วัตต์รวม = TDP ของ CPU + TBP ของการ์ดจอ + วัตต์เมนบอร์ด (ไม่กรอก = 50 W) + 5 W ต่อแรม 1 แถว + 7 W ต่อ SSD + 10 W ต่อ HDD + ชุดระบายความร้อน (ซิงก์ลม 5 W · ชุดน้ำ 15 W) + 15 W (พัดลมเคสและ USB)
> PSU ที่แนะนำ = วัตต์รวม × 1.30 แล้วปัดขึ้นเป็นหลัก 50 W

ตัวอย่างจากหน้าจอจริง (รูปที่ 4.6): Core i5-14400F (65) + RTX 5060 Ti (180) + เมนบอร์ด (50) + แรม 2 แถว (10) + SSD 1 ตัว (7) + พื้นฐาน (15) = **327 W** → แนะนำ PSU อย่างน้อย 327 × 1.3 = 425.1 → **450 W** ส่วน PSU ที่เลือกไว้ 650 W ใช้อยู่ 50% จึงผ่าน

**ตัวกรองอัจฉริยะ:** ตอนเลือกอะไหล่ ระบบลองใส่แต่ละรุ่นลงในสเปกแล้วรันกฎชุดเดียวกัน ถ้าเกิดปัญหาระดับผิดพลาดใหม่ รุ่นนั้นใส่ไม่ได้ ผู้ใช้เลือกได้ว่าจะซ่อนรุ่นที่ใส่ไม่ได้ หรือแสดงทุกรุ่นพร้อมป้ายเหตุผล ค่าเริ่มต้นคือแสดงทุกรุ่น เพื่อให้ผู้ใช้เรียนรู้จากคำเตือน

**รูปที่ 3.11 Flowchart จัดสเปกตามงบ** → `docs/diagrams/img/flow-budget.png`

3. ตรวจด้วย Engine ตัวเดียวกับหน้าจัดสเปก ถ้าผิดพลาดหรือเกินงบ ลดรุ่นทีละขั้น ถ้าเหลือเกิน 5% อัปเกรดการ์ดจอหรือ CPU
4. สร้าง 3 ตัวเลือก: ประหยัด (ประมาณ 85% ของงบ) · สมดุล (ประมาณ 100%) · คุ้มสุด

ถ้าผู้ใช้ "ยอมใช้มือสอง" ระบบใช้ราคากลางมือสองแทนราคาใหม่ในหมวดที่ยอม (ค่าเริ่มต้นทุกหมวดยกเว้น PSU เพราะ PSU มือสองที่เสียอาจทำให้อะไหล่อื่นเสียด้วย)

### 3.7 ราคามือสองและอะไหล่ที่มีแต่มือสอง

**รูปที่ 3.12 Flowchart เลือกแหล่งราคากลางมือสอง** → `docs/diagrams/img/flow-used-price.png`

ราคากลางมือสองเลือกจาก 3 แหล่งตามลำดับ
1. รายงานจากสมาชิกที่แอดมินอนุมัติ ในช่วง 60 วัน (ต้องมีอย่างน้อย 3 รายงาน ตัดค่าผิดปกติด้วย IQR แล้วใช้มัธยฐานถ่วงน้ำหนัก)
2. ราคาที่แอดมินสำรวจตลาดเอง ไม่เกิน 90 วัน
3. สูตรประมาณค่าเสื่อม: ราคามือสอง = ราคาใหม่ × rᵗ × k (r = สัดส่วนราคาที่เหลือต่อปีของหมวด, t = อายุเป็นปี, k = ตัวคูณเกรด A 1.00 / B 0.90 / C 0.75)

**อะไหล่ที่มีแต่มือสอง:** รุ่นเก่าที่เลิกขายมือหนึ่งแล้วใช้ช่องราคาเป็น "ราคาตอนเปิดตัว" สำหรับสูตรค่าเสื่อมเท่านั้น
- ทุกจุดที่อ่านสภาพของชิ้นเรียกฟังก์ชันกลาง `effectiveCondition()`: รุ่นที่มีแต่มือสองถูกคิดเป็นมือสองเกรด B เสมอ แม้ข้อมูลที่ส่งมาจะเป็น "มือหนึ่ง" (รวมตอนบันทึกสเปกฝั่งเซิร์ฟเวอร์)
- จัดตามงบใช้รุ่นเหล่านี้เฉพาะเมื่อผู้ใช้ยอมมือสองในหมวดนั้น และมีราคากลางมือสอง
- หน้าจัดสเปกมีแถบ "สภาพอะไหล่" ตั้งสภาพของชิ้นที่เพิ่มต่อจากนี้ และเปลี่ยนทั้งชุดเป็นมือสองได้ในครั้งเดียว

### 3.9 การออกแบบความปลอดภัย

| ภัย | วิธีป้องกันในระบบ |
|---|---|
| ผู้ใช้ทำรายการเกินสิทธิ์ | ทุก Server Action ตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์ก่อนทำงาน ไม่เชื่อค่าจากหน้าเว็บ |
| ข้อมูลผิดรูปแบบ / SQL Injection | ตรวจค่าทุกตัวด้วย Zod และใช้ Drizzle ORM ที่ส่งค่าแยกจากคำสั่ง SQL |
| เดารหัสผ่าน | เข้าสู่ระบบผิด 5 ครั้งใน 15 นาที (ต่อบัญชีและต่อ IP) ล็อกชั่วคราว |
| ไฟล์อันตราย | อัปโหลดรูปตรวจชนิดไฟล์จากเนื้อไฟล์จริง (Magic Bytes) จำกัด 2 MB และตั้งชื่อใหม่แบบสุ่ม |
| XSS / Clickjacking | Header ความปลอดภัย: Content-Security-Policy, X-Frame-Options DENY, X-Content-Type-Options, Strict-Transport-Security |

### 4.5 ข้อจำกัดที่พบ (ใช้ในบทที่ 5 ได้)

- **ยังไม่มีระบบส่งอีเมล:** การส่งอีเมลยืนยันต้องใช้โดเมนของตัวเอง ระหว่างนี้ผู้ใช้ล็อกอินด้วย Google หรือให้แอดมินกด "ยืนยันอีเมลให้"
- **ยังไม่มีที่เก็บรูป:** อะไหล่แสดงไอคอนของหมวดแทนรูปจริง ตั้งค่าเพิ่มได้ภายหลังโดยไม่ต้องแก้โค้ด
- **อะไหล่ในระบบยังน้อย (40 รุ่น):** งบขั้นต่ำสำหรับเล่นเกมอยู่ที่ประมาณ 39,000 บาท ถ้าเพิ่มรุ่นราคาประหยัดหรือรุ่นเก่าแบบมีแต่มือสอง งบขั้นต่ำจะลดลงเอง
- **ราคาอ้างอิงไม่ได้อัปเดตอัตโนมัติ:** แอดมินต้องแก้ราคาเองหรือนำเข้า CSV เพราะระบบตั้งใจไม่ดึงข้อมูลจากเว็บร้านค้าโดยตรง
- **หน้า "ไม่พบ" ส่งรหัส 200:** เป็นข้อจำกัดของโหมด Cache Components ใน Next.js หน้าแสดงข้อความถูกต้อง และมี noindex กัน Search engine เก็บ
